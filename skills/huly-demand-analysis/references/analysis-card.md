# 需求分析卡规范

## 结论标签

每个有判断含义的条目必须使用以下一种标签：

- `[FACT][USER_INPUT]`：原始反馈直接证明。措辞应体现“反馈称”或“用户提出”。
- `[FACT][HULY_XX]`：Huly 标题或正文可以直接证明。使用检索结果中的证据 ID。
- `[HYPOTHESIS]`：根据输入或资料推导的可能解释，不得使用“就是、确定、必然”等事实措辞。
- `[UNKNOWN]`：当前资料不足。写明缺少什么，以及需要向谁确认或通过什么数据确认。

同一条内容不要混合多个标签。需要同时表达事实与推测时拆成两条。

## 输出结构

### A. 原始反馈理解

- 谁提出
- 谁在使用
- 使用场景
- 反馈中的现象
- 反馈中的问题表达
- 用户提出的解决方案

### B. Huly 检索过程

- 实际使用的多个搜索方向
- 扫描的 Documents、Issues、Cards 数量
- 最相关资料：标题、类型、摘要、来源链接、相关原因、证据 ID
- 没有找到的资料类型也要明确说明

### C. 需求分析（18项，全部必填）

1. 需求类型
2. 用户角色
3. 使用场景
4. 用户提出的解决方案
5. 当前观察到的现象
6. 真正的核心问题
7. 用户目标
8. 已确认事实
9. AI 推测
10. 当前未知的信息
11. 相关历史需求
12. 相关 Bug
13. 已有产品能力
14. 用户影响
15. 业务影响
16. 风险影响
17. 信息缺口
18. 推荐下一步

每项至少有一条内容；无法判断时必须写 `[UNKNOWN]`，不能留空。

## 推荐下一步顺序

推荐动作应优先覆盖：

1. 验证失败发生在哪个创建阶段，以及失败对象是否安全重试。
2. 收集失败率、影响用户数、错误码、失败原因和重试结果。
3. 核实历史能力、已有入口和技术约束。
4. 明确批量任务的成功、部分成功、失败状态定义。
5. 在上述事实确认后，再比较“重试失败项、重新提交整个批次、展示错误原因”等方案。

不要在证据不足时直接给出开发范围、交互稿或确定方案。
