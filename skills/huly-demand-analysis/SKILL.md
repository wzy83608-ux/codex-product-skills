# 用户反馈与需求分析

## 通用原则

本 Skill 不依赖固定目录、专用脚本、Huly 连接或其他 Skill。输入可以是用户反馈、访谈、工单、文档、日志、截图、数据摘要或 Huly 资料。没有外部证据时仍可分析，但必须把未证实内容标为 `HYPOTHESIS` 或 `UNKNOWN`。

## 工作流程

1. 区分反馈提出者、实际用户、使用场景、观察现象、问题表达和用户提出的方案。
2. 把用户提出的按钮、页面或自动化方式保留为方案输入，不直接当成底层需求。
3. 识别实际使用者、需求提出者、决策者和受影响者；从关键角色的任务、触发场景、期望结果、阻碍与代价进行推演。角色或动机没有直接证据时必须标为 `HYPOTHESIS` 或 `UNKNOWN`。
4. 明确需求目的：区分用户想达成的结果、业务希望改善的结果和用户提出的实现方式；目的应描述可观察的改善，不得把功能名称直接当成目的。
5. 若可访问资料源，围绕问题、场景、失败模式、恢复路径、历史能力和规则做最小必要检索；资料不可用时记录 Information Gap。
6. 阅读 [需求分析卡规范](references/analysis-card.md)，生成带 `FACT/HYPOTHESIS/UNKNOWN` 标签的分析卡。
7. 把第一版视为草稿，阅读 [需求分析 Reviewer](references/reviewer.md)，核对事实、数字、因果、引用、角色推演、需求目的和遗漏。
8. 输出审查摘要和修正版需求分析；不得为了完整而编造数据、角色动机或根因。

## 输出边界

输出核心问题、角色关系、关键角色推演、场景、用户目标、需求目的、证据、假设、未知项、影响、信息缺口和建议验证动作。角色推演用于提出可验证的需求假设，不替代用户研究或业务确认。除非用户明确要求且目标系统可用，否则不保存正式流程记录、不写回 Huly，也不自动进入评审、优先级、设计或 PRD。
