# 需求质量与证据评审

## 通用原则

本 Skill 可审查用户直接提供的需求分析、问题定义或证据包，不依赖固定目录、记录库、版本编号、专用脚本或其他 Skill。若存在 Huly 或其他资料源，只做最小必要的只读核验；不可访问时明确证据限制。

## 评审流程

1. 检查输入是否包含 Core Problem、Target User、Scenario、User Goal，以及事实、假设、未知项和来源。
2. 站在实际使用者当时的任务、环境、能力、频率、时间压力和失败后果中检查：需求是否解决真实任务，是否可理解、可执行、可恢复，新增收益是否可能被操作成本、学习成本或使用限制抵消。
3. 分别评估实用性与用户价值。实用性关注真实场景中是否用得上、用得顺；用户价值关注是否改善任务结果、效率、准确性、风险或体验。不得仅因功能完整、界面新增或业务方提出就判定有价值。
4. 核对事实是否被证据完整支持，是否存在时态、模块、角色、版本或因果偷换。没有用户证据的角色状态、行为和价值判断必须标为假设或未知。
5. 检查 Solution Bias、逻辑跳跃、矛盾、重复需求、已有能力、历史问题和当前产品规则。
6. 将信息缺口分为 `BLOCKING` 与 `NON_BLOCKING`，只让真正会改变问题定义、范围、实用性或价值是否成立的缺口阻塞。
7. 仅自动修正术语、标签、重复、格式和可直接恢复的引用；业务含义、范围、规则、用户价值和取舍交给责任人确认。
8. 输出 `PASS`、`CORRECTED` 或 `NEED_HUMAN_CONFIRMATION`，并列出使用者视角摘要、实用性、用户价值、Finding、证据、严重度、Owner 和下一步。

## 可选方法

需要更严格审查时，可按任务读取 `references/` 中的就绪检查、正式评审、上下文核验、人工确认或最终确认方法。它们是方法参考，不构成本地工具依赖，也不要求自动进入后续流程。

## 使用者视角边界

使用者视角是基于现有证据的情境推演，不替代访谈、可用性测试或上线数据。实用性和用户价值使用 `HIGH/MEDIUM/LOW/UNKNOWN` 表达，并说明证据、适用角色与场景；它们不等于业务价值、投入产出比或需求优先级。
