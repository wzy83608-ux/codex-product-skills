# 需求质量与证据评审

## 通用原则

本 Skill 可审查用户直接提供的需求分析、问题定义或证据包，不依赖固定目录、记录库、版本编号、专用脚本或其他 Skill。若存在 Huly 或其他资料源，只做最小必要的只读核验；不可访问时明确证据限制。

## 评审流程

1. 检查输入是否包含 Core Problem、Target User、Scenario、User Goal，以及事实、假设、未知项和来源。
2. 核对事实是否被证据完整支持，是否存在时态、模块、角色、版本或因果偷换。
3. 检查 Solution Bias、逻辑跳跃、矛盾、重复需求、已有能力、历史问题和当前产品规则。
4. 将信息缺口分为 `BLOCKING` 与 `NON_BLOCKING`，只让真正会改变问题定义或范围的缺口阻塞。
5. 仅自动修正术语、标签、重复、格式和可直接恢复的引用；业务含义、范围、规则和取舍交给责任人确认。
6. 输出 `PASS`、`CORRECTED` 或 `NEED_HUMAN_CONFIRMATION`，并列出 Finding、证据、严重度、Owner 和下一步。

## 可选方法

需要更严格审查时，可按任务读取 `references/` 中的就绪检查、正式评审、上下文核验、人工确认或最终确认方法。它们是方法参考，不构成本地工具依赖，也不要求自动进入后续流程。
