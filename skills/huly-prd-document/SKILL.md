# PRD 需求文档生成与审查

## 通用原则

本 Skill 不依赖固定目录、专用脚本、本地记录库、特定版本编号或其他 Skill。输入可以是产品设计、会议决定、原型、需求分析、用户资料、Huly 证据、历史产品文档或可核验的公开资料。缺失正式版本链时仍可生成 `STANDALONE_DRAFT`。

PRD 中的事实、规则、结论、指标、流程和范围必须有明确依据。允许的依据类型为：用户或业务事实、互联网来源、过往产品资料、经确认的业务知识、可核验的行业知识。AI 常识、合理猜测和未经确认的经验不能作为确定内容写入 PRD，只能进入待确认项或被省略。

## 工作流程

1. 阅读 [证据与引用规则](references/prd-evidence-policy.md)，建立证据账本并判断每项输入可支持什么内容。
2. 阅读 [PRD 就绪检查方法](references/prd-readiness-method.md)，判断现有证据是否足以支持用户要求的内容；真正影响范围、规则、权限或验收的缺口应阻塞。
3. 阅读 [PRD 输出格式](references/prd-structure.md)，按参考文档的章节顺序组织内容。没有适用内容或可靠依据的模块直接省略，不生成空标题、空表格或占位文字。
4. PRD包含产品流程图或交互原型图时，读取 [PRD视觉资产规则](references/prd-visual-assets.md)。流程图必须使用 `$fireworks-tech-graph` 生成，并作为图片直接显示在“产品流程图”正文位置，不能只提供图片路径或附件链接；原型必须给出已验证存在的绝对本地文件地址。
5. 生成正文时读取 [PRD 草稿生成规则](references/prd-draft-generation.md)，为事实性内容建立来源映射。
6. 审查时读取 [PRD Reviewer](references/prd-reviewer.md)，检查格式、证据、完整性、视觉资产和是否存在捏造；区分安全的编辑修正与需要业务 Owner 决定的问题。
7. 需要人工确认或最终审批时，读取对应参考方法；没有记录系统时以带日期、Owner 和版本标识的普通文档记录，不伪造正式 Gate 状态。

## 边界

不重新分析需求，不替用户选择产品方案，不改变已确认范围，不把模板中的编辑提示当成PRD正文，不编写技术架构或开发任务，不声明开发已经获准，也不自动写回任何外部系统。公开资料需要检索时只做与当前PRD相关的最小必要查询，并在正文或附录给出可访问来源、标题和检索日期。
