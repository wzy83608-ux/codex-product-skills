# PRD 输出格式

## 格式来源

按用户提供的《产品需求文档》Markdown模板组织PRD。模板里的操作提示、示例值、空行、星标提示、飞书同步块说明和示例链接只用于理解版式，不复制到正式正文。

## 章节顺序

保持以下顺序，只输出适用且有依据的章节。没有内容的章节、二级模块、表格或列可以省略，不得为了版式完整填入猜测或占位内容。

1. `# 产品需求文档`
2. `# 前言`：仅在有必要说明文档目的、适用范围或阅读方式且有依据时出现。
3. `# 一、版本信息`：可包含版本号、创建日期、审核人；未知字段不编造，可省略。
4. `# 二、变更日志`：仅记录真实发生且可追溯的变更，使用“时间、版本号、变更人、主要变更内容”表格。
5. `# 三、文档说明`：按需包含“名词解释”。只有正文使用了确需解释的术语时才生成术语表。
6. `# 四、需求背景`：按证据情况包含“业务价值”“产品/数据现状”“用户调研”“竞品分析”。
7. `# 五、需求范围`：描述有依据的In Scope；Out of Scope只有被明确确认时才写。
8. `# 六、功能详细说明`：按需包含“产品流程图”“交互原型图”“功能说明”。产品流程图必须在对应标题下作为可见图片直接显示在PRD正文中，不能只写图片地址或附件链接；同时保留SVG源文件地址。交互原型图必须提供已验证存在的绝对本地文件地址。功能说明优先使用“序号、模块、功能、功能详细说明、交互图”表格；复杂规则、状态、异常、权限和验收标准可作为对应功能下的三级小节或表格，不另造无关顶级章节。
9. `# 七、非功能需求`：只记录有明确来源的性能、可靠性、容量、安全、隐私、合规、兼容、运营、财务、法务、帮助或反馈要求。
10. `# 八、埋点`：只记录已确认的事件、参数、口径或数据要求；没有依据时整节省略。
11. `# 九、项目规划`：只记录已确认的里程碑、Owner、依赖或计划，不推测研发工期。
12. `# 附录`：列出正文真实引用的资料及链接，可包含数据分析、用户调研、设计分析、历史产品、业务规则、行业资料和互联网来源。

## 功能内容映射

原始资料中的用户流程、功能需求、业务规则、状态、异常、权限、页面交互、验收标准和依赖，应放在“六、功能详细说明”中对应的功能项下。不要因为模板没有独立顶级章节就丢失已有且重要的产品信息。

## 证据呈现

正文保持可读，不要求每句话都堆叠长链接。使用简短来源标记，如 `[E01]`，并在附录建立“依据清单”，记录依据类型、来源标题或记录、相关章节、日期、链接或文档ID。没有可核验来源的内容不得伪装成事实。
